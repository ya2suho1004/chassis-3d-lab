## 0단계 이후의 인수 순서

아래 문안은 한 번에 모두 실행하라는 명령이 아니다. 각 단계에 필요한 기준과 권한이 갖추어진 뒤 해당 문안을 선택한다. 정확한 완료 기준은 [06_MVP_ROADMAP.md](docs/06_MVP_ROADMAP.md)를 따른다.

### A. 과제 규칙과 데이터 검증

```text
승인된 0단계 점검을 바탕으로 domain과 설정 검증의 최소 범위를 구현하라. UI/3D보다 먼저 데이터 계약과 순수 판정을 검증하라.

기존 tasks.json은 문자열 절차와 recordSheet의 참고자료, forms.json은 과제 참조 인덱스다. judge.js를 복사하지 말고 자동 기준값·음수/공백/Infinity·알 수 없는 앞뒤·빈 규칙·반올림 경계를 교정하라. 승인된 단위·수식·기준이 없으면 notEvaluable이다.

차량 verdict, 학생 first/final 정오, NPC 최종수행 통과를 분리하라. 판독·계산·판정 답을 별도로 보존하라. 미승인 실제 배치·기준은 null로 두고 연구평가를 차단하라. 가짜 사례 테스트와 교사 검토 사례를 분리하라.

스키마 형식/의미 검증, 경계값, 불량 차량을 정확히 판정한 학생의 통과, 첫 오답 후 보완통과의 첫답 보존을 증거로 보고하라. 모르는 정비 수치를 채우지 말라.
```

### B. 로컬 저장과 결과 화면

```text
IndexedDB에 수행 초안·의미 이벤트·확정 payload·deliveryEnvelope를 저장하는 작은 흐름을 구현하라. 3D 없이 일반 HTML 화면으로 검증하라.

과제 수령 시 recordId를 한 번 만들고 첫 draft transaction complete 후 진행하라. 응답 제출 직후 저장, 새로고침 같은ID 복원, 결과 freeze, 다음 학생 화면 초기화와 과거 outbox 보존을 구현하라. 네트워크 await를 쓰기 트랜잭션 안에 넣지 말라.

저장 실패·용량 부족·두 탭·복원·숨김시간 제외·강제종료의 한계를 시험하라. 연구내용과 전송상태를 섞지 말고 CSV에 recordId/버전을 남겨라. 한도 초과시 사건을 자르지 말라. 실제로 확인한 저장·복원 증거만 보고하라.
```

### C. 자동 제출의 작은 연결 시험

```text
사용자가 선택한 시험 계정·배포 범위 안에서만 같은 출처 /api/submissions→Apps Script→비공개 Sheet의 최소 제출 경로를 구현하라. 실제 학생 대신 가짜 코드와 별도 시험 Sheet를 사용하라. 계정·요금·권한 설정에서 추가 확인이 필요하면 정확한 제안과 이유를 제시하라.

서버 비밀은 서버 설정에만 둔다. 공개 세션 읽기와 제출 외에 학생용 전체 조회/교사 변경 API를 만들지 말라. JCS UTF8 SHA256을 양끝에서 검증하고 모든 쓰기는 ScriptLock 규약을 따른다. 같은 ID/같은 내용은 같은 receipt, 다른 내용은 충돌이다. Sheet의 한 정본 행에서 요약/이벤트를 파생하라.

처음 정상 접수, 서버 저장 후 응답 유실, 같은 ID 동시 요청, 다른 내용 충돌, HTML200/깨진JSON/잘못된hash, quota/timeout, 새로고침 후 확인 재전송을 시험하라. 학생 화면 receipt와 정본 recordId/receipt/hash 및 재시도 후 추가 정본행 없음까지 대조하라. no-cors나 HTTP200만으로 성공 처리하지 말라.
```

### D. 실제 배치와 캐릭터·NPC

```text
교사가 제공한 손 스케치·사진 44장·상대 배치표와 (확보되면) 실측 치수를 사용해 배치 데이터를 먼저 만들고 평면도와 최소 도형으로 검토하라. 실측이 없는 위치·크기는 null로 두고 상대 배치만 ‘임시 개념 배치’로 표시하라. 북쪽·동쪽은 막힌 면, 남쪽·서쪽은 엔진·전기 구역과 개방 연결된 열린 면이며 섀시 구역 별도 입구를 만들지 말라. 교사 확인 전 layoutConfirmed=false이며 실제 재현 완료라고 하지 말라.

승인된 배치에 학생 캐릭터·NPC·제동력 시험기 접근점과 단순 보행을 붙여라. 3인칭을 기본 제안으로 하되 키보드/터치의 동일 핵심동작, 흔들림 없는 카메라, Escape, HTML 안내를 제공하라. 다른 장비는 실제 위치 식별용으로 두고 기능을 늘리지 말라.

현실 동선·장비 위치의 교사 비교검토와 학교기기 성능을 확인하라. 성능 예산은 목표이며 실측 결과와 구분하라. 외부 에셋은 개별 라이선스 확인 후 사용하라.
```

### E. 제동력 단일 과제 연결

```text
승인된 단계·안전·측정세트를 장면에 연결하라. NPC 과제 수령→안전→탐색→준비→측정/정지→판독→계산/판정→NPC 보완/통과→결과·접수를 끝까지 연결하라.

안내와 무안내는 같은 판정 엔진을 쓰고 피드백 정책만 분리하라. 최초 답 저장 뒤 실제 UI 노출시 feedbackShown을 기록하라. 무안내에도 안전경고를 유지하며 첫답이 무지원응답이라는 보장은 하지 말라. 시작 displayMode와 전환 이력·경험모드를 보존하라.

잘못된 순서·안전준비 미완료·판독/계산/판정 오류·NPC 보완·불량차량 정답통과·응답유실·다음학생 이전기록 재전송을 실제 화면에서 확인하라. 실습통과·기기저장·서버접수를 따로 표시하라.
```

### F. 수업 운영·현장 검토

```text
교사가 개발자 도구 없이 비공개 Sheet 설정탭에서 과제·세션·승인기준 버전·모드를 선택하고 검사후공개하는 최소운영을 구현/검증하라. 학생은 읽기전용 세션스냅샷만 받는다. 연구사용허용·실제 IRB/동의·접근자/보관/폐기는 연구자가 확인한다.

학교 PC와 태블릿의 기기명/OS/브라우저를 기록하고 키보드·터치·학교망·오프라인·재시작·WebGL 실패·동시제출을 시험하라. 서버는 오프라인 기기의 미접수 기록을 알 수 없으므로 학생 receipt와 별도 배부코드 목록 대조를 제공하라.

비교학급의 없는 앱 로그를 0으로 넣지 말고 공통 외부 평가도구를 사용하라. 배치재현/판독학습/연구기록/운영수용을 교사와 점검하고 미확인·실패를 남겨라. 별도 승인 전 push나 실제 수업 데이터 수집을 하지 말라.
```
