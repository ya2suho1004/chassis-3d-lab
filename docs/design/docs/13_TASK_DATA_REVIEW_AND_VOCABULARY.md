# 13 과제 데이터 독립 검토와 등록명 사전

작성일: 2026-10-21(한국) · 범위: 설계·계약 검토 · 앱·서버 실행, 설치, 배포, 학생자료 수집 없음

**결정:** 0A의 교사 확인값과 12단계는 보존한다. 등록명은 [task-vocabulary.v1.1.0.json](../contracts/task-vocabulary.v1.1.0.json)에 정의한다. 이 사전은 구현 전에 합의할 뜻과 검증 규칙이며, 구현 코드의 동작 검증이나 실제 장비의 안전 승인을 뜻하지 않는다. 현장 장비의 측정값 고정 동작, 단계 안의 안전 검사 시점, 승인 상태의 출처 표현을 정리하기 전에는 두 사례를 운영 준비가 끝난 과제로 표시하지 않는다.

## 2. 보존할 교사 확인값과 승인 표현

| 항목 | 보존할 값 |
|---|---|
| 측정 | 후륜, 단위 표기 `kg`, Lv1 240/200/600, Lv2 250/190/600 |
| 기준 | 편차 ≤8%, 뒤축 합 ≥20%, 앞축 합 ≥50%. 경계 포함 |
| 산식 | 편차 `abs(left-right)/axleWeight*100`, 합 `(left+right)/axleWeight*100` |
| 정밀도 | 중간 계산은 원값, 최종 계산 기재는 소수 첫째 자리 절사, 판정도 기재값. 측정 입력은 정수 |
| 조작 | 0A의 12개 stepId와 순서, 6개 안전조건 keep, 숫자식 표시 |

독립 검산은 다음과 같다. 이는 검토자용 표이며 무안내 학습 화면의 제목이나 사전 안내로 복사하지 않는다.

| 사례 | 편차 원값 → 기재·판정값 | 합 원값 → 기재·판정값 | 사례의 차량 판정 |
|---|---|---|---|
| Lv1 | 40/600×100 = 6.666… → 6.6 | 440/600×100 = 73.333… → 73.3 | 양호(pass) |
| Lv2 | 60/600×100 = 10 → 10.0 | 440/600×100 = 73.333… → 73.3 | 불량(fail), 편차 조건 불충족 |

`kg`는 두 교사 사례에서 쓰는 현장 표기 그대로 보존한다. 이를 `kgf`·`N`으로 자동 치환하거나 질량과 힘이 일반적으로 같다고 선언하지 않는다. 다른 단위나 다른 장비의 수치를 섞어 계산하는 것은 별도의 승인된 변환 규칙이 필요하다.

검토 시점의 두 과제는 `approvalStatus=approved`, `ruleset.approvalStatus=approved`, `approvedAt=2026-10-21T00:00:00+09:00`였다. 반면 0A 최상위는 `pending`이며 note는 이 응답으로 승인 버전을 만든 뒤 앱에 반영하라고 한다. 따라서 **개별 교사 응답이 확인됐다는 사실**과 **변환된 과제의 운영 승인 상태**를 구별한다. 날짜만 받은 응답에 자정 승인 시각을 붙이지 않는다. 1.1.0 반영 시 과제는 미해결 동작·안전 연결을 표시하는 pending을 유지하고, 개별 응답은 원문 참조와 날짜로 보존한다. 교사 값·순서를 다시 묻는 절차는 필요하지 않다.

## 3. 12단계와 NCS·조작부 대조

NCS의 15개 번호를 12개 학습 단계로 묶은 **학교 과제의 요약**이다. 0A는 이 12단계를 ok로 확인했다. 번호 수가 다르다는 이유만으로 단계를 추가·삭제하거나 순서를 다시 묻지 않는다. 다만 묶인 단계 안에서 빠진 관찰·안전 확인을 “이미 구현됨”으로 해석하면 안 된다.

| 과제 단계 | 근거 대응 | 확인 결과와 남은 계약 문제 |
|---|---|---|
| `ppe` | p.97 안전·유의사항 | 안전화 필수, 위험 작업 보안경이라는 NCS 문구보다 학교 0A는 두 보호구 확인으로 구체화. 해당 학교 조건으로 보존 |
| `tire` | p.98(1) | 원문은 마모 점검·이상 시 교체. 공기압 육안 점검은 0A에서 확인한 추가 문구. 육안 관찰을 압력 수치 측정으로 기록하지 않음 |
| `equip` | p.98(2)(1~4) | 오일 댐퍼·롤러 이물질·컴프레서·모든 스위치 OFF 후 전원 ON이 대응. 묶인 항목을 `inspected=true` 클릭 하나로 모두 관찰했다고 간주하지 않음 |
| `enter` | p.98(3)(4)(7) | 시험할 차축·중앙 위치를 묶은 학교 요약. “조향 정위치”만으로 원문의 조향 이상·떨림 확인과 이상 처리까지 완료했다고 할 수 없음. 원문 (7)은 METER 다음이나 학교의 통합 단계 순서는 0A대로 보존 |
| `axle` | p.98(5), 14번 `AXLE Load` | 이름은 일치. 축중 응답의 유효 제출과 정답 여부를 분리 |
| `mode` | p.98(6), 14번 `BRAKE` | 원문은 METER ON·P/L·영점 확인. 학교는 BRAKE 선택. 버튼 이름은 확인되나 기능 등가는 미확인. 디지털 표시이므로 “지침 0”을 아날로그 계기 승인으로 해석하지 않음 |
| `lower` | p.99(8), 14번 `LIFT UpDn` | 하강과 주변 확인은 대응. 눌렀다는 명령과 실제 하강 확인을 구별 |
| `motor` | p.99(9), 14번 `MOTOR` | ON·정상 롤러 회전은 대응. 원문의 P/L 확인이 현장 디지털 장비에서 어떤 상태인지 동작 매핑에 포함 |
| `press` | p.99(10), p.97 안전 | 서서히 끝까지 브레이크 조작이 대응. 측정 중 가속 금지는 지속 조건이며 가상 조작으로 실제 답력 숙련을 측정하지 않음 |
| `read` | p.99(11)(12) | **차이:** 원문 (11)의 METER OFF·롤러 정지·표시 고정 확인이 현재 instruction에 없음. 디지털 장비에서 최대값을 고정하는 실제 동작을 확인해야 함. METER라는 가짜 버튼을 만들거나 BRAKE를 임의로 같은 기능으로 취급하지 않음 |
| `off` | p.99(13)(14) | MOTOR OFF→리프트 상승→차량 이탈의 순서는 대응. 세 행동에 서로 다른 시점의 안전 조건이 필요함 |
| `calc` | p.99(15)·p.99~100 산식 | 현재 6응답과 산식은 대응. instruction의 “조치 기재”는 requiredResponseItems에 없음. 채점 항목으로 몰래 추가하지 말고, 운영 전 비채점 설명인지 별도 응답인지를 과제 변경 기록에서 명시 |

METER 대응 확인은 0A의 교사 선택을 다시 묻는 일이 아니다. 장비 지침이나 실제 조작 증거로 **표시 고정·롤러 정지의 동작**을 확인하는 기술 확인이다. 확인 전에는 해당 부분을 가상으로 성공시켰다고 기록하지 않는다. 두 사례 모두 source.document에 NCS·사진·0A를 한 문자열로 합쳐 `confirmation=approved`를 적었는데, 이 표현도 각 자료의 확인 범위를 넘는 동작 등가 승인으로 읽히지 않도록 한다.

## 4. 선행 단계와 안전 연결

두 사례의 `steps`와 `feedback`은 동일하다. 12개 stepId는 유일하고 현재 prerequisites는 `ppe → tire → equip → enter → axle → mode → lower → motor → press → read → off → calc`의 한 줄 연결이다. 없는 ID·자기 참조·순환은 없다. 앞 단계 완료만으로 현재의 안전 상태를 보증할 수 없으므로 안전은 별도로 평가한다.

| 안전 ID | 원문·교사 확인 범위 | 현재 연결 | 조정할 연결과 검사 시점 |
|---|---|---|---|
| `s-ppe` | p.97 + 0A keep | tire~off | 대체로 일관. ppe 단계에 자기 조건을 달 필요는 없음. 조작 중 현재 착용 상태를 검사 |
| `s-lift` | p.97은 상승·하강 모두 주변 사람·장애물 확인, 0A는 주변 사람 확인 keep | lower만 | off 안의 **상승 직전**에도 연결. 이전 하강 확인을 재사용하지 않음 |
| `s-motor` | p.98~99의 정위치→MOTOR 순서, 0A의 중앙 미정위치 ON 금지 keep | motor | 현재 중앙 상태를 검사. enter 완료 이력만 검사하지 않음 |
| `s-exit` | p.99 OFF→상승→이탈, 0A 회전 중 이탈 금지 keep | off | **실제 이탈 직전** 검사. off 전체 진입 때 true를 요구하면 MOTOR가 켜진 동안 OFF 동작도 막히는 순환 차단이 생김 |
| `s-accel` | p.97 가속 조작 유의, 0A 측정 중 금지 keep | press만 | 측정 상태 전체의 금지 행동에 연결. motor~read 동안 가속 버튼이 노출된다면 동일하게 차단·기록 |
| `s-engine` | 원문은 가능한 한 시동 OFF, 0A는 측정 외 점검 시 OFF keep | 없음 | tire/equip 점검에 연결해야 함. 측정 중 무조건 시동 OFF라는 새 규칙으로 확대하지 않음. 엔진 상태·차단 피드백 연결은 아직 없음 |

`requiredSafetyConditions`라는 배열만으로 off 내부의 시점 차이를 표현할 수는 없다. 이번 사전은 행동별 평가 범위를 정의한다. 향후 구현에서 등록 완료 규칙이 하위 행동을 구별해 검사하도록 하되, 검사 실패를 이유로 안전한 정지 행동 자체를 막아서는 안 된다. Schema는 ID의 등록 여부까지만 확인하고, 실제 평가 순서는 구현 검증 항목으로 남긴다.

6개 안전조건을 보존했다고 해서 모든 위험을 재현한 것은 아니다. 0A의 범위 밖에서 시뮬레이터가 실제 장비 안전을 보증하거나 새로운 필수 안전수치를 만들어서는 안 된다.

## 5. 등록명과 검증 책임

등록 목록의 정본은 [task-vocabulary.v1.1.0.json](../contracts/task-vocabulary.v1.1.0.json)이다. 각 이름에 뜻·허용상태·검증 규칙을 둔다. 대소문자·이름이 맞지 않으면 거절하며 `eval`이나 자동 별칭으로 보정하지 않는다.

| 종류 | 등록명 | 주의점 |
|---|---|---|
| 완료 규칙 | `ppeConfirmed`, `inspected`, `vehicleCentered`, `axleWeightRead`, `brakeModeSelected`, `liftLowered`, `motorOn`, `pedalPressed`, `readingsSubmitted`, `vehicleExited`, `answersSubmitted` | `inspected`는 현재 stepId별 결과. 판독·계산의 제출 완료와 정답을 분리 |
| 미승인 예시의 차단 규칙 | `teacherApprovalRequired` | pending 예시에서만 허용. approved에서는 거절. 완료될 수 없는 이름 |
| 채점 규칙 | `decimalExact`, `vehicleVerdictMatch` | 십진 수치 동등성·차량판정 일치. 차량판정/학생정오/NPC/업로드 상태를 구별 |
| 예비 채점 규칙 | `absoluteTolerance` | 04 §3의 기존 후보. 명시적 승인 허용오차가 있을 때만 사용. 이번 두 사례에는 사용하지 않음 |
| 정밀도 정책 | `integer`, `truncate1` | 측정 정수 입력과 계산 소수 1자리 응답은 다른 범위. 계산 응답 10과 10.0은 수치상 동일 |
| 계산 규칙 | `axlePercentDeviation`, `axlePercentSum` | 식은 설명용. 적용 축·단위·유한값·분모 양수 검증이 먼저 |
| 안전조건 | `s-ppe`, `s-lift`, `s-motor`, `s-exit`, `s-accel`, `s-engine` | 충족/불충족/미확인을 구분. 미확인은 안전 통과가 아님 |

사전의 `implementationVerification=notPerformed`는 의도적인 제한이다. “개발자가 검증한 등록 목록”은 향후 개발자가 각 이름을 실제 연산에 연결하고 해당 조건을 검증한 뒤에만 말할 수 있다. 지금 검증한 것은 문서의 뜻, JSON 문법, 참조·목록의 일관성, 두 고정 사례의 산술이다.

Schema는 등록명 enum, 자료형·범위, approved에서의 필수값을 검사한다. 별도 계약 검증은 ID 유일성, 선행 그래프 비순환, 장비 참조, 안전·피드백 참조, 등록명과 응답 종류의 조합을 검사한다. 원문 진위·장비 동작·승인 근거의 적합성은 두 검사만으로 증명되지 않는다.

## 6. 정밀도 적용 범위

`decisionPrecision={mode:rounded,digits:1,rounding:truncate}`는 기존 구조로 표현 가능하다. `rounded`는 이 계약에서 절사도 포함하는 기존 필드명이다. 1.1.0에서 비교값 출처를 `judgmentValueSource=written`으로 명시하면 “판정 비교값=기재값”의 뜻이 고정된다. `measurement.inputsIntegerOnly=true`는 판독 입력 범위에 해당하며, 편차·합의 소수 응답까지 정수로 제한하지 않는다.

`truncate1`은 최종 기준 산출값을 절사하는 정책이다. 학생의 6.69를 다시 6.6으로 절사해 정답으로 받아들이는 정책은 아니다. 계산 응답은 첫째 자리보다 세밀한 비영 소수를 거절하거나 정답과 다르게 처리하고, 최초 제출은 보존한다. 수치상 같은 `10`과 `10.0`은 같게 채점하고 표시를 `10.0`으로 맞출 수 있다. 이 구분은 미세한 이진 부동소수 오차에 의한 잘못된 절사를 막는 검사와 별개다.

경계 검증에서는 7.99→7.9(양호), 8.00→8.0(양호), 8.09→8.0(양호), 8.10→8.1(불량)을 구별한다. 합은 19.99→19.9(불량), 20.00→20.0(양호)이다. 이는 0A의 절사값 판정·경계 포함을 설명하는 계산 예시이며 새 사례 세트를 승인한 것이 아니다.

## 8. 무안내 모드의 사전 정답 노출

검토 당시 제목에는 Lv1의 “양호”와 240/200/600, Lv2의 “편제동 불량”과 250/190/600이 있었다. **학습 화면의 제목으로 쓰면 판독과 판정의 답이 시작 전에 노출된다.** 제목은 사례 A/B 같은 중립 문구로 바꾸고, 수치·정답은 검토 자료와 채점 설정에 보존한다. 시험 계기에서 학생이 읽도록 보이는 값과 제목에 답을 써 두는 것은 서로 다르다.

내부 `caseId`의 `ok`·`deviation` 같은 판정 단서, 파일명·난이도 설명의 good/bad 표기, measurement·ruleset·feedback을 포함한 전체 task JSON을 학생에게 보여 주는 요약 화면에도 그대로 출력하지 않는다. 학생 화면에는 단계·계기 표시·입력 영역 등 해당 시점에 필요한 내용만 바인딩하고, 검토자용 정답 자료와 구별한다. 단, 브라우저에 내려간 설정은 개발자 도구로 열람할 수 있으므로 UI 분리를 정답의 비밀 보장으로 표현하지 않는다. 공식 시험 보안은 별도 설계가 필요하다.

또한 wrong_calc의 `뒤축 600`은 축중 판독의 답이고, wrong_verdict는 계산 후 판정에 쓰는 기준을 알려 준다. 안전 피드백은 즉시 유지하되, 무안내 최초 응답을 독립적으로 해석하려면 **6개 항목의 첫 응답을 같은 일괄 제출로 먼저 고정한 뒤 비안전 정오 피드백을 보여 주는 정책**을 권고한다. 공개 전 수치·판정을 자동 안내하거나 이미 제출한 한 항목의 해설로 미제출 항목의 답을 알려 주지 않는다.

기존 04 §6의 “무안내에서도 설명적 오류 피드백 유지”와 충돌하지 않는다. 첫 응답 묶음을 고정한 직후 해설을 주고 보완 응답을 받는다. 다른 제출 단위나 즉시 피드백을 채택한다면 `feedbackPolicyVersion`에 사전 고정하고 후속 답에 영향을 줄 수 있음을 기록한다. 피드백이 실제 보인 뒤 `feedbackShown`·종류·key·항목을 남기며, 이를 이해했다는 증거로 해석하지 않는다.

## 9. 차량 진입 방향의 소유권

**방향은 세션 설정에서 교사가 선택하고 수행 시작 스냅샷에 고정한다.** 과제 데이터는 후륜 측정이라는 요구와 지원 가능한 진입을 설명한다. rear를 북/남 방향으로 해석하지 않는다. 북·남 모두 가능한 현장 조건은 보존하고 기본값은 `null`로 둔다. 미선택 상태에서 방향에 의존하는 3D 차량 이동을 자동 시작하지 않는다.

권장 후속 필드는 `sessionConfiguration.vehicleEntryDirection: north|south|null`이다. 1.1.0의 현 저장 계약에 이 필드가 없다면 이번 사전만으로 기록 저장이 지원되는 것은 아니다. 세션 계약에 필드를 추가하거나 방향을 포함한 불변 설정을 `sessionSnapshotId`가 참조하도록 개정한 뒤 사용한다. layout의 방위와 대조하고, 전진/후진 조작을 방향에서 자동 추론하지 않는다. 기존 수행을 새 방향으로 바꾸지 않는다. 이 결정은 기본 진입 방향을 새로 확정한 것이 아니다.

## 10. 다음 단계와 검증 한계

Claude에 넘길 다음 한 단계는 **1.1.0 계약·사전과 원문을 대조해, 12단계 안의 동작 매핑·안전 검사 시점·피드백 노출을 구현 전 점검표로 고정하는 것**이다. 특히 read의 최대값 고정/정지, off의 정지→상승→이탈, s-engine의 점검 연결이 핵심이다. 앱 구현 시작 여부는 사용자 결정이다.

1.1.0 반영본을 다시 읽어 두 과제의 제목이 “사례 1/사례 2”로 중립화되고 최상위가 pending인 것을 확인했다. 규칙 자체의 교사 승인값은 `ruleset.approvalStatus=approved`로 보존되며, `approvedAt=null`과 `approvedOn=2026-10-21`로 시각·확인일을 구별한다. 새 `feedbackPolicy`는 `status=proposed`이고 `unguidedAnswerFeedback=afterAllFirstResponses`, `safetyFeedback=immediate`이다. 따라서 일괄 최초 응답 뒤 해설은 설계 제안 상태이며 구현됐다고 표시하지 않는다.

이 검토에서 수행한 것은 원문 대조, 등록명·참조 검토, 고정 사례 산술 검산이다. 사전이 올바른 JSON이라는 사실은 장비 상호작용 검증, 3D 동선 검증, 운영 안전 승인, 연구 사용 승인을 뜻하지 않는다. 기존 교사 응답과 원자료는 보존한다.
