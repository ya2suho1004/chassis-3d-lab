## 2. 재유입 위험 (합성 시험 결과)

| 상황 | 결과 | 절차에서 막는 방법 |
|---|---|---|
| 기기에서 접수 확인된 기록, 서버 줄 삭제 | 전송·강제 재전송을 눌러도 **다시 가지 않음** | 없어도 안전. 다만 기기에 남아 있으면 대조에서 "서버에 없음"으로 뜨므로 기기도 비운다 |
| 접수 확인 전 기록(응답 유실 포함), 서버 줄 삭제 | 전송 버튼을 누르면 **다시 들어옴**, 접수번호도 새로 나옴 | 기기를 먼저 처리하고 서버를 나중에 지운다 |
| 다른 학생 기록을 보내려고 전송 버튼 사용 | 코드를 가리지 않아 **철회자 미접수 기록도 함께 감** | 3단계 표의 B. 서버 삭제 전에 끝낸다 |
| 철회한 코드를 다시 사용 | 서버가 **막지 않음** | 코드를 다시 나눠 주지 않는다 |
| 접수 기간(`SUBMIT_ACCEPT_UNTIL`) 경과 뒤 전송 | 새로 들어오지 않음 | 회수 못 한 기기가 있을 때의 보조 수단 |
| 기기 저장소를 비운 뒤 전송 | 보낼 것이 없음, 대화 사본도 없음 | 3단계 |

앱은 자동으로 전송하지 않는다. 전송은 교사 화면 버튼으로만 일어나므로 버튼을 누르지 않으면 수행 기록은 들어오지 않는다.

## 3. 처리 순서

**순서를 지킨다: 멈춤 → 대상 확인 → 기기 → 서버 → 파일 → 재점검.** 서버를 먼저 지우면 기기에 남은 기록이 다시 들어올 수 있다.

### 0단계. 접수와 대상 확정
독립 담당자가 요청을 받는다. 대응표로 **세션 코드 + 익명 코드**, 사용한 기기, 내려받은 파일 목록을 확인한다. 코드만으로 전체를 찾아 지우지 않는다(코드를 다른 세션에서 다시 썼을 수 있다).

### 1단계. 멈춤
- 수업 중이면 교사 화면 ② 수업 중에서 그 세션의 AI 교관을 끈다.
- 그 코드를 다시 나눠 주지 않는다.
- 기기 담당자에게 3단계 지시 전까지 전송 버튼을 누르지 말라고 알린다.

### 2단계. 서버 미리보기
`1_미리보기.sql`에 세션 코드와 익명 코드를 넣어 Supabase SQL Editor에서 실행한다. 지우지 않는다. 건수를 처리 기록지에 적는다. `other_session_*` 줄이 나오면 대응표로 같은 학생인지 확인한다. 같은 학생이면 그 세션도 따로 처리한다.

### 3단계. 기기 처리 (사용한 기기마다)
교사 화면 ③ 수업 후에서 교사 로그인 후 "이 기기 전송 상태"를 본다.

| 경우 | 할 일 |
|---|---|
| **A.** 다른 학생 기록이 모두 접수 확인됨, 끝내지 않은 수행 없음 | "이 기기와 대조"로 확인한 뒤 바로 사이트 데이터 삭제. 철회자의 미접수 기록은 보내지 않고 사라진다 |
| **B.** 다른 학생 기록에 전송 대기·접수 확인 필요가 있음 | 대기 기록 전송, 필요하면 강제 재전송으로 모두 접수 확인. **철회자 미접수 기록도 함께 서버로 가며 이를 처리 기록지에 적는다.** 2단계를 다시 실행해 건수를 고친 뒤 사이트 데이터 삭제 |
| **C.** 다른 학생의 끝내지 않은 수행이 있음 | 초안은 전송도 내려받기도 안 되고 삭제하면 복구할 수 없다. 그 학생이 같은 코드로 이어서 끝내게 한 뒤 B. 끝낼 수 없으면 연구자가 정할 때까지 삭제를 보류하고 이 기기의 전송을 멈춘다 |
| **D.** 다른 학생 기록에 거절·충돌이 있음 | 다시 보낼 수 없다. ZIP에는 철회자 기록도 들어 있으므로 연구자가 그 기록의 보관 방법을 정할 때까지 삭제를 보류한다 |
| **E.** 기기를 회수할 수 없음 | 처리 기록지에 적고 6단계 재점검을 유지한다. 재유입 차단 기능은 없으므로 접수 기간을 앞당길지 연구자가 판단한다 |

사이트 데이터 삭제는 Chrome 설정의 사이트 설정에서 앱 주소를 찾아 지운다(**메뉴 이름은 학교 태블릿에서 확인 필요**). 앱 탭을 닫고 한다.
- **함께 지워지는 것:** 그 기기의 모든 학생 기록·대화 사본·초안·캐릭터, 교사 수업 설정, 연습 규정값. 삭제 뒤 수업 설정을 다시 해야 한다.
- **미접수 자료는 확보 전에 지우지 않는다**(계획서 4-3). A~D 표는 이를 지키기 위한 것이다.
- **확인:** 앱을 다시 열어 시작 화면 아래 "확정 기록 0건 (전송 대기 0건)"을 본다.
- **다운로드 폴더:** 1절 파일을 직접 지운다.

### 4단계. 서버 삭제
모든 기기 처리가 끝난 뒤 `2_서버삭제.sql`에 네 값을 넣어 실행한다. 건수가 미리보기와 다르면 아무것도 지워지지 않고 오류가 난다. 그때는 2단계부터 다시 한다. 끝나면 `1_미리보기.sql`을 다시 실행해 `records`, `chat_logs` 줄이 없는지 본다. 교사 계정의 앱 화면에는 삭제 권한이 없으므로 Supabase 관리 계정으로 한다.

### 5단계. 내려받은 파일
- 4단계 **뒤에** 서버 CSV·ZIP을 새로 받아 옛 파일을 대체하고, 옛 파일을 복구 곤란한 방법으로 지운다. 줄을 손으로 지우지 않는다(ZIP 원본·해시와 어긋난다).
- 이 기기 묶음(`device`)·대조표 CSV에도 철회자가 들어 있다. 다시 만들 수 없으면 파일째 지운다.
- 분석본은 그 코드를 뺀 자료로 다시 산출한다. 이미 공개된 결과와 완전 익명 집계는 제거하지 못할 수 있다(계획서 4-3).
- 복사본이 있는 곳(외장 저장장치, 메일, 클라우드)을 처리 기록지 목록과 맞춘다.

### 6단계. 재유입 재점검
`1_미리보기.sql`을 다시 실행한다. **처리 직후, 그 세션의 마지막 수업 뒤, 분석 자료를 고정하기 전** 세 번 본다. 줄이 다시 보이면 어느 기기에서 왔는지 찾아 3단계부터 반복한다.

### 7단계. 기록
아래 처리 기록지를 동의·철회 이력과 함께 분리 보관한다. 요청자 이름을 쓰지 않는다.

## 5. 지금 할 수 없는 것
- 공유 기기에서 **특정 코드만** 지우기. 사이트 데이터 전체 삭제뿐이다.
- 전송할 때 철회자만 빼기.
- 삭제한 기록·철회한 코드의 재접수를 서버에서 차단하기.

## 7. 서류에 맞출 곳 (Hermes)
- **수집항목표 54줄** "교사가 교사 화면에서 접수 확인분 삭제": 그런 기능이 없다. "접수 확인 뒤 사이트 데이터 삭제"로 고치거나, 기능을 만들기로 하면 그때 유지.
- **수집항목표 62줄(6절)** "가명 코드로 서버의 수행·대화 기록을 찾아 삭제하고, 내려받은 CSV에서도 지운다": 계획서 4-3보다 좁다. 세션 + 코드로 찾는 것, 기기 저장소, 가리기 전 질문이 있는 대화 사본, ZIP·JSON·대조표, 분석본, 재유입 점검을 넣는다. "교사만"은 "Supabase 관리 계정 보유자"로.
- **연구계획서·설명문**: 기기 사이트 데이터 삭제 때 다른 학생 자료를 확보한 뒤 지운다는 점이 "미전송 자료는 확보 전에 지우지 않는다"와 이미 맞는다. 고칠 것 없음.

## 8. 합성 리허설 (실제 사용 전, MOON 허락 뒤)
실제 서버를 쓰므로 허락을 받고 한다. 브랜치를 합치고 재배포한 뒤에 할 수 있다(전송 버그 수정이 공개판에 아직 없음).
1. 리허설 세션에서 합성 코드 D-98, D-99로 태블릿에서 각각 끝까지 수행한다. D-99는 AI 교관에 합성 질문을 1개 한다.
2. D-98만 전송되도록 한 번 보내 접수 확인까지 받는다. D-99는 대기로 둔다.
3. D-99를 철회 대상으로 정하고 3단계 표의 경우를 판단해 0~6단계를 그대로 따른다.
4. 확인할 것: 삭제 스크립트 실행과 건수 불일치 시 되돌림, D-98이 서버에 남는지, 사이트 데이터 삭제 메뉴 경로, 삭제 뒤 "0건" 표시, 수업 설정 재설정, 처리 기록지 작성에 걸리는 시간.
5. 결과로 이 문서의 "초안"과 미확인 표시를 고친다.
