# 정리 화면과 수행 뒤 둘러보기 — 설계 (2026-11-16)

MOON 요청·승인: 2026-11-16("추천대로 진행" — 아래 결정 가·나·다 모두 추천안).

## 요청
1. 실습장 화면에서 캐릭터 머리 위에 닉네임이 보인다.
2. 검사를 통과한 뒤에도 실습장 화면이 이어져, 남은 시간에 장비를 둘러보며 도감을 모은다. 지금 마지막 화면의 "JSON 내려받기"처럼 학생에게 필요 없는 것은 없앤다.
3. 수행 뒤 정리 화면에서 잘한 점·보완할 점·어려웠던 점과 방금 쓴 공식·규정값을 정리해 준다. 이 화면은 30초 동안 넘길 수 없고, 그 뒤 "실습장으로 이동"을 누르면 실습장으로 돌아간다.

## 결정 (MOON 2026-11-16)
- **가. AI가 맡는 범위**: 사실(공식·규정값·정오·횟수)은 앱이 과제 자료와 기록에서 그대로 가져오고, AI는 그 사실을 받아 "교관의 정리" 말만 쓴다. AI를 쓸 수 없으면 앱이 규칙으로 만든 정리를 보인다.
- **나. 둘러보는 중 과제 다시 받기**: 없음. 다시 하려면 "마치기" 뒤 처음 화면에서 시작한다(지금과 같은 새 수행).
- **다. 두 단계로 나눔**: 1단계(서버 변경 없음) = 닉네임, 새 흐름, 정리 화면(규칙 정리 + 공식·규정값 + 30초). 2단계 = AI의 말(서버 함수·지시문). 서버 반영은 MOON이 "서버 반영해"라고 할 때만.

## 흐름
- 지금: 검사 통과 → 결과 화면(정비 일지·상태 칸·요약·표·JSON/CSV·교사용 상세·"다음 학생") → 시작 화면
- 바꾼 뒤: 검사 통과(또는 중단) → **정리 화면**(30초) → "실습장으로 이동" → **수행 뒤 둘러보기** → ☰ 메뉴 "마치기" → 시작 화면

기록은 지금처럼 검사 통과·중단 순간에 확정·전송한다. 정리 화면과 둘러보기는 기록(payload)에 아무것도 더하지 않는다. 기록 형식·채점·전송 로직(`src/domain`, `src/delivery`, `src/records`)은 고치지 않는다.

## 1단계

### 1-1. 머리 위 닉네임
- `LabScene`의 학생 캐릭터(`Avatar`) 머리 위에 기존 이름표 방식(drei `Html` + `label3d`)으로 닉네임을 띄운다. 높이는 머리 바로 위(키 + 0.15 안팎 — 교관 이름표의 0.33은 따라가기 시점에서 머리와 너무 떨어져 보임). 누를 수 없다(`pointerEvents: none`).
- 캐릭터가 숨는 때(1인칭 보기, 교관 대화 중)에는 함께 숨는다.
- 장비 이름표와 구별되는 모양(클래스 `label3d me`).
- 닉네임은 지금처럼 기록·서버·AI 요청에 넣지 않는다.

### 1-2. 정리 화면 (지금의 결과 화면을 바꿈)
화면 이름(`result`)과 구성요소(`ResultScreen`)는 그대로 쓰되 내용을 바꾼다. 위에서부터:

1. 제목과 정비 일지(`WorkLog`) — 그대로.
2. 기록 한 줄 — 상태 3칸(실습 결과·이 기기 저장·온라인 접수)을 없애고 한 줄만:
   - 수업용 세션: 지금의 전송 상태 줄(`sendLine`) 그대로
   - 그 밖(시연·리허설): "기록을 이 기기에 저장했어요."
   - 기록 없이 하기: 지금 문구 그대로("저장·전송되지 않았습니다" 계열)
   - 저장 실패: 지금의 저장 실패 카드와 "다시 저장" 그대로
3. 내 답 표(판독·계산·판정의 최초·최종 ✓✗) — 그대로. 정답 값은 계속 숨긴다(MOON 결정 ④, 2026-11-10).
4. **교관의 정리** — 세 묶음: 잘한 점 / 보완할 점 / 어려웠던 것으로 보이는 점. 1단계는 규칙으로 만든다(아래 1-3).
5. **오늘 쓴 공식과 규정값** — 과제 자료에서 가져온다(아래 1-4).
6. 단추 줄 — "실습장으로 이동"(주 단추)과 "마치기". 둘 다 화면이 뜬 뒤 30초 동안 눌리지 않고, 주 단추에 남은 초를 보인다("실습장으로 이동 (27)"). 30초는 모든 세션·조건에 같다. 뒤로 가지 않는 시계로 세고(기기 시계를 바꿔도 같음), 풀릴 때 화면 낭독기에 한 번 알린다. 단추 줄 아래 안내는 학생 말로 한 줄("‘마치기’를 누르면 처음 화면으로 돌아가요. 저장된 기록은 지워지지 않아요.").

없애는 것(학생 화면): "JSON 내려받기", "이 수행 CSV 내려받기", "교사용 상세 기록 보기", 상태 3칸, "요약" 목록의 수업 시점·조건 줄, "다음 학생"(→ "마치기"). 교사는 교사 화면 ③ 수업 후의 요약 CSV·연구용 묶음으로 받는다(지금도 있음, 교사 로그인 뒤).
남기는 수치: 걸린 시간, 학습 오류 수, 안전 위반, 힌트, NPC 검사 횟수는 "교관의 정리" 위나 안에 짧게 보인다.

저장 실패 상태(`saveError`)에서는 "실습장으로 이동"을 보이지 않는다. 지금처럼 "다시 저장"과 "마치기"(한 번 더 확인)만 둔다. 저장이 되면 "실습장으로 이동"이 나타난다. 이 상태의 저장 실패 카드 안에만 "기록 파일 내려받기"(JSON)를 둔다 — 기록을 건질 마지막 길이라 남긴다(검토 반영). 평소 화면과 기록 없이 하기에는 내려받기가 없다.

### 1-3. 규칙으로 만든 정리 (`src/app/debrief.ts`, 순수 함수)
입력: 응답 요약(`ResponseSummary`), 수행의 횟수들(오류 유형별·안전 위반·힌트·검사 횟수), 완료 여부, 조건. 출력: `{ good: string[]; improve: string[]; hard: string[] }`.
- 잘한 점: 묶음(판독·계산·판정)을 처음부터 모두 맞힘, 안전 위반 없음(통과한 수행에서만 — 받자마자 중단한 수행을 칭찬하지 않게), 검사 한 번에 통과, 힌트 없이 마침.
- 보완할 점: 처음 틀렸다 고친 항목(항목 이름만), 끝까지 틀린 항목, 안전 위반 유형, 순서 오류, 중단.
- 어려웠던 것으로 보이는 점: 가장 많이 난 오류 유형, 힌트를 쓴 횟수, 검사를 여러 번 받음.
- 해당하는 것이 없는 묶음은 고정 문장 한 줄.
- **넣지 않는 것**: 사례의 측정값·계산 기준값·정답 판정(양호/불량), 학생이 넣은 값. 항목 이름과 맞음/틀림 사실만 쓴다(표에 이미 보이는 것).
- 문장은 고정 틀에 항목 이름·횟수만 끼운다. 같은 입력이면 같은 출력.

### 1-4. 공식과 규정값 (`debrief.ts`의 `debriefFacts(task)`)
- 과제 자료의 `feedback.wrong_calc.why`(공식), `feedback.wrong_verdict.why`(판정 기준)를 그대로 보인다. 학교 승인 문구이고 수행 중 피드백으로 이미 쓰는 글이다.
- 사례 값(`measurement.*`, `caseId`)은 쓰지 않는다. 시험으로 지킨다: 같은 과제의 사례 1·2에서 이 구역의 글이 같아야 한다.

### 1-5. 안내 없음 규칙
- 정리 화면은 수행이 확정된 뒤에 나온다. 검사를 통과한 수행은 모든 최초 응답이 저장돼 있으므로 정답 관련 피드백 시점 규칙(`feedbackPolicy`)에 걸리지 않는다.
- **중단한 수행**에서 `answerFeedbackAllowed`가 거짓이면(안내 없음 + 최초 응답이 다 차지 않음) 공식·규정값 구역과 정오에 기대는 정리 문장을 보이지 않고 "과제를 끝까지 마치면 공식과 규정값을 볼 수 있어요." 한 줄로 대신한다. 수치 줄의 "학습 오류 n번"도 뺀다(오답이 더해진 수라 숫자만으로 정오가 드러남 — 검토 반영). 내 답 표의 지금 동작은 바꾸지 않는다(이 경우 표에는 낸 답의 ✓✗가 원래부터 보인다 — MOON 확인 대기).

### 1-6. 수행 뒤 둘러보기
- `App`의 `lab` 화면 상태에 "수행을 마친 뒤"임을 나타내는 값을 더한다(예: `after: 'completed' | 'aborted' | null`). `run`은 `null`.
- 지금의 "과제 받기 전 둘러보기"와 같되:
  - 교관에게서 과제를 다시 받을 수 없다. 교관은 "오늘 의뢰는 끝났어. 남은 시간엔 장비를 둘러보면서 도감을 채워 봐."라고 말한다.
  - 화면 위 안내: 통과면 "의뢰 완료 — 장비를 눌러 도감을 모아 보세요.", 중단이면 "장비를 눌러 도감을 모아 보세요."
  - ☰ 메뉴(게임 화면), 오른쪽 위 안내 카드, 기본 화면 머리에 "마치기"가 있다. 누르면 지금의 "다음 학생"과 같다(기록 모드면 `repo.clearCurrent()` 뒤 시작 화면).
  - 교사용 배치 눈검토·실측 입력 단추는 이 상태에서 보이지 않는다(학생 수행 직후 화면이므로).
- 장비 누르기·도감·리프트·연습·AI 질문은 지금 둘러보기와 같다(기록 없이 하기는 AI 없음 그대로).
- 둘러보는 중 새로고침하면 지금처럼 시작 화면으로 간다(확정 기록은 그대로 있다).
- 자동 전송은 화면과 무관하게 계속 돈다.

### 1-7. 앱 판
한 단계 올린다(구현 직전에 main의 지금 판을 확인하고 그다음 번호). 채점·기록 형식은 그대로이고 수행 뒤 화면과 흐름이 달라진다.

### 1-8. 시험
- `debrief`: 묶음별 문장, 값 누출 없음(사례 값·학생 입력값이 출력에 없다), 사례 1·2의 공식·규정값 글이 같다, 중단 + 안내 없음 + 최초 응답 미완이면 가린다.
- 정리 화면: 30초 전에는 두 단추가 눌리지 않고 남은 초가 보인다, 30초 뒤 눌린다, 내려받기·교사용 상세가 없다, 저장 실패면 "실습장으로 이동"이 없다, 기록 없이 하기 문구.
- 둘러보기: 수행 뒤 상태에서 과제 받기가 없고 "마치기"가 있다.
- 닉네임 이름표: 캐릭터와 함께 그려지고 1인칭에서는 없다.
- 기존 시험 중 결과 화면의 옛 구성을 고정한 것은 새 구성에 맞게 고친다.

## 2단계 — AI의 말 (MOON 승인 2026-11-16 "추천대로 진행")

지시문 초안·입력 본보기·화면 규칙: `docs/copy/2026-11-16_AI정리_지시문_초안.md`(이 문서가 지시문의 정본 초안이다).

### 2-1. 길
- 새 함수를 만들지 않는다. 지금 대화 함수(`supabase/functions/chat`)가 요청의 `protocolVersion`으로 갈래를 나눈다: `chat-1`은 지금 그대로, `debrief-1`은 새 처리 본체로. 앱은 지금의 대화 주소(`VITE_CHAT_ENDPOINT`)를 쓴다 → Vercel 환경값을 더하지 않는다.
- DB 이관을 하지 않는다. 정리 로그는 `chat_logs`에 남기고 `prompt_version`이 `debrief-`로 시작하는 것으로 가른다(지시문 판 `debrief-ko-0.1.0`). 대화 한도를 세는 쿼리는 이 행을 빼고, 정리 한도는 이 행만 센다. (처음 안은 `kind` 열 이관이었으나, 이관·배포 순서·교사 화면 호환 위험을 없애려고 바꿈.)
- 서버가 옛 판이면 `debrief-1` 요청은 `INVALID_REQUEST`로 거절되고 화면은 규칙 정리를 쓴다 → 앱을 서버보다 먼저 올려도 안전하다.

### 2-2. 요청 (`debrief-1`, text/plain JSON, 16KB 이하, 모르는 키 거부)
`{ protocolVersion, sessionCode, anonymousStudentCode, recordId(필수), taskId, difficultyMode, facts }`
`facts = { items: [{ itemId, first: true|false|null, final: true|false|null }], errorTypes: {키: 횟수}, safetyViolationTypes: {키: 횟수}, hintCount, npcInspectionCount, durationSeconds|null }`
- 서버는 과제별 허용 목록으로 검사한다: `itemId`는 그 과제의 응답 항목과 정확히 같아야 하고(묶음 판독·계산·판정도 서버가 안다), 오류·안전 키는 알려진 키만, 횟수는 0~999 정수. 자유 글은 받지 않는다.
- 항목·오류·안전 키의 한글 이름과 묶음은 `scripts/build-chat-context.mjs`가 과제 자료와 `src/app/resultLabels.ts`에서 뽑아 `taskContext.generated.json`에 넣는다(단일 원본, 최신 여부 시험). 사례 값은 넣지 않는다.
- 학번(`anonymousStudentCode`)과 `recordId`는 로그·한도·재사용에만 쓰고 AI 회사로 보내지 않는다(대화 기능과 같음).

### 2-3. 처리 순서 (`_shared/chat/debriefCore.ts`, 지시문은 `debriefPrompt.ts`)
1. 검사 실패 → `INVALID_REQUEST`.
2. 세션이 없거나 꺼져 있거나 `chatbot_enabled`가 거짓 → `CHAT_DISABLED`.
3. 같은 `recordId`·세션·학번의 정리 로그(`answered`)가 있으면 저장된 글을 그대로 돌려준다(모델을 부르지 않음).
4. 한도: 학생 하루 10번(상수), 세션 하루 `chat_daily_cap`(정리 행만 셈) → `LIMIT_STUDENT`/`LIMIT_SESSION`.
5. 서버가 요약 글을 만들고 지시문과 함께 모델을 부른다(대화와 같은 제공자·모델, 429는 대화와 같이 1번 다시).
6. 답 검사: JSON 하나(코드 표시는 벗겨 읽음), `good`·`improve`·`hard`가 문자열 목록, 묶음마다 3문장 이하, 문장마다 120자 이하, "양호"·"불량" 없음, 답의 숫자는 모두 지시문·요약에 있는 숫자. 어기면 `status: 'error'`로 로그를 남기고 `DEBRIEF_INVALID`.
7. 통과하면 로그(`question_masked` = 요약 글, `answer` = 정리 JSON, `status: 'answered'`)를 남기고 `{ ok: true, notes: { good, improve, hard }, logged, chatId, reused }`.

### 2-4. 앱
- 정리 화면이 뜰 때 한 번 부른다. 조건: 검사 통과한 수행, 기록 모드, 대화 주소가 있음, 확정 기록의 `recordId`가 있음, 온라인. 같은 수행에 두 번 부르지 않는다(개발 모드의 두 번 마운트 포함).
- 기다리는 동안 "교관이 정리를 쓰고 있어요…", 8초 안에 오지 않거나 실패하면 규칙 정리. 한번 보인 글은 바꾸지 않는다. 30초 잠금은 지금처럼 화면이 뜬 때부터.
- AI 글이면 제목 옆에 "AI 교관이 쓴 글이에요(사람 아님)." 빈 묶음은 지금의 고정 문장.
- 수치 줄, 내 답 표, "오늘 쓴 공식과 규정값"은 그대로 앱이 만든다.
- AI 글은 수행 기록·기기 저장에 넣지 않는다(화면 상태뿐).
- 교사 화면의 대화 점검: `prompt_version`이 `debrief-`로 시작하는 행을 "수행 정리"로 표시한다(열은 이미 있음).

### 2-5. 시험·평가
- 서버 본체: 가짜 DB·가짜 모델로 처리 순서 전부(재사용, 한도 분리, 답 검사 각 조건, 대화 한도가 정리 행을 세지 않음), 요약 글에 사례 값·학번이 없음, 과제 문맥 최신 여부.
- 앱: 부르는 조건, 8초 뒤 규칙 정리, 늦게 온 답 무시, AI 표시, 빈 묶음.
- 평가 도구 `scripts/chat-eval/run-debrief.mjs`: 합성 수행 요약 10개 안팎, 기본은 계획만 출력하고 `--run`일 때만 실제 모델을 부른다. 결과는 `docs/chat-eval/`. 실제 실행은 지휘 세션이 MOON 승인(2026-11-16)에 따라 서버 반영 전에 한다.

### 2-6. 반영 순서 (각각 MOON이 말할 때만)
1. 서버 반영: `supabase functions deploy chat`(이관 없음). **이때 아직 서버에 올리지 않은 E2(끊기거나 막힌 답 처리, b4da704)도 함께 올라간다.**
2. 앱 재배포.
- 수업용 세션(CLS-L12·CLS-L5)은 AI가 꺼져 있다. 수업에서 AI 정리를 쓰려면 교사 화면에서 그 세션의 AI를 켠다.
- 앱 판을 한 단계 올린다(구현 직전에 main의 판 확인).

## 하지 않는 것
- 학생이 직접 쓰는 소감 칸.
- 수행 횟수(`retryCount`) 채우기, 같은 화면에서 다시 하기.
- 도감을 기록·서버에 남기기.
